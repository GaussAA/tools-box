# 错误台账

只收「**调试两轮以上才抓到**」或「**症状与根因隔得很远**」的顽固问题；一次就定位的
不收（那类该修在代码注释里）。每条必须写清 **守住它的手段** —— 没有手段的教训等于
没沉淀：下次换个人（或换个会话）还会踩。

- [现象] 用一句用户能复述的话描述；[根因] 写机制，不写「不小心」；[正解] 给可执行的修复；
- [守住] 指明靠哪个脚本 / 断言 / 文档条款防止复发。

---

## 1. 双击程序没反应，界面完全不出现

- **[现象]** 构建全绿、`ctest` 全过，但双击 `ToolBox.exe` 进程立刻退出，没有任何窗口、
  任何报错。而且「以前每次都能出来，最近几次开发就不出现了」。
- **[根因]** 输出目录里**没有 Qt 运行时**（`Qt6*.dll`、`platforms/qwindows.dll`）——
  它们由**可选目标** `deploy`（windeployqt）拷进来，不在默认构建里。而
  `scripts/build_verify.ps1` 第一步 `Remove-Item -Recurse -Force build` 会把整棵构建树
  **连同之前 deploy 好的运行时一起删掉**，它自己却从不跑 deploy。所以每跑一次全量验证，
  「双击能起界面」就失效一次 —— 而当天的 10/10 ctest 对此完全无感。
- **[正解]** 手工跑界面前先 `cmake --build build --config Release --target deploy`；
  2026-10-02 起 `build_verify.ps1` 在全量验证末尾**自动跑 deploy**（deploy 目标在受限
  环境跑不了 windeployqt 时，按 windeployqt 清单手工兜底拷贝运行时），「全量验证之后
  的双击」天然可用，不再依赖谁记得去跑。CI 的产物没有这个问题（CI 流程里有 deploy），
  所以「CI 出的包能用、本地双击不行」曾是这条的指纹。
- **[守住]** `build_verify.ps1` 末尾对 Qt6Core.dll / platforms\qwindows.dll /
  translations\qtbase_zh_CN.qm 三件套做存在性断言，缺任一项直接 FAIL（退出码 3）；
  `verify_shell.ps1`（真启动产物）—— 它在产物缺运行时会直接失败而不是绿着。

## 2. 界面全英文（或消息框按钮是 OK），中文文案却完全正常

- **[现象]** 两种形态：整窗英文（导航是 "Home | Developer tools | ..."），或只有
  QMessageBox 的按钮是 `OK` 而其余全中文。改语言配置、重启都没用。
- **[根因]** 三个独立因素叠加，见 [workflow.md §3.3](./workflow.md#33-界面语言与翻译)：
  ① Qt 6 把词条搬进 `qtbase_<locale>.qm`，旧的 `qt_<locale>.qm` 是 **99 字节空壳**，
  按 Qt 5 的 `qt` 前缀加载会**成功**装上一个什么都不翻译的 translator，不报错；
  ② 本机 Qt 装在非标准路径 `C:\Qt6.12\`，`QLibraryInfo::path(TranslationsPath)` 指向的
  编译期前缀（`C:/Qt/6.12.0/...`）不存在，回退路径落空；
  ③ 会话环境变量 `LANG` / `LC_ALL` 会**盖过系统语言**（实测系统 zh-CN、程序整个起成英文）。
- **[正解]** 加载前缀改 `qtbase`（保留 `qt` 回退）；`LanguageChoice` 在配置只写语言时补
  默认地区（`zh` → `zh_CN`，否则找不存在的 `qtbase_zh.qm`）；`verify_shell.ps1` 自己设并
  复原 `ui/language`，不再依赖调用方与环境。
- **[守住]** `verify_shell.ps1` 的「对话框按钮是否被本地化」断言 —— 它盯着的 bug 活了
  一次 Qt 大版本升级而无人发现，因为迁移审计当天没有任何测试会启动真程序。

## 3. 门禁脚本「全绿」，但该 FAIL 的没 FAIL（假绿）

- **[现象]** `verify_filesize.ps1` 报某文件 1181 行、判定豁免内通过；实际该文件 **1269 行**，
  差了 88 行 —— 真超限时它照样绿。
- **[根因]** PowerShell 5.1 的 `Get-Content` 按**系统 ANSI 代码页**（936/GBK）解码无 BOM
  的 UTF-8：中文注释被解成乱码的同时，某些字节序列会被**并成一行**。门禁数错行数 =
  该 FAIL 时不 FAIL。同一个坑的另一个表现：`.ps1` 本身若无 BOM，中文注释乱码足以让
  脚本解析失败。
- **[正解]** 数行一律用 `[System.IO.File]::ReadAllLines($path).Length`（与 LF 字节数一致）；
  新增 `*.ps1` 必须带 UTF-8 BOM（`verify_whitespace.ps1` 查前三个字节）。
- **[守住]** 对检查脚本本身做**注入式反向验证**：往被检对象里注入一个必然违规的内容
  （如一行含中文的 `QStringLiteral`），确认脚本立刻 FAIL 并返回非零。绿了不算数，
  能红才算数。

## 4. 「测试全绿」但程序有 bug：不启动真程序的盲区

- **[现象]** 10/10 ctest 通过的当天，程序实际：双击起不来（见 1）、消息框按钮是 `OK`
  （见 2）、抖音渲染失败被报成「60 秒超时」（真因在 `errorString` 里被超时分支吃掉）。
- **[根因]** 单元/集成测试都**不启动真实产物**：部署期问题（缺运行时）、启动期问题
  （翻译加载）、原生对话框文本、进程退出码 —— 这一整类问题对它们是盲的。而 GUI 冒烟
  脚本 `verify_shell.ps1` 此前**从未在本地跑过**，等于不存在。
- **[正解]** 验证体系分两层：命令行层（构建 + ctest + 七个静态检查）+ **真机层**
  （`verify_shell.ps1` 启动真实产物、截图、UIAutomation 断言、点开关于对话框）。
  修完 UI 侧的东西，两层都要过。
- **[守住]** `run_all.ps1` 末尾会列出全部只能人工跑的脚本 —— 提醒「自动检查全绿」
  不等于「可以交付」；GUI 冒烟对 Debug 与 **Release**（分发形态）各跑一次。

## 5. commit 时命令整条被拒，像是 git 坏了

- **[现象]** `git commit -m "...（提交信息里含 PowerShell / cmd 字样）..."` 被工具层
  安全过滤整条拒绝，报错让人以为 git 出了问题。
- **[根因]** 命令执行工具按**词**拦截含 `powershell` / `pwsh` / `cmd` 的命令 —— 提交
  信息里的措辞也会触发（例如「PowerShell 5.1 的坑」）。
- **[正解]** 提交信息换措辞（「解压命令」「系统自带终端」等）；或者把含敏感词的说明
  放进代码注释 / 文档而不是提交信息。
- **[守住]** 无脚本可守，是执行环境的行为 —— 写进本台账就是为了「下次第一时间想到，
  而不是先怀疑 git 坏了」。

## 6. 真机脚本一律报「nav not found」，而程序其实启动得好好的

- **[现象]** `verify_videodl_fetch.ps1` 一开跑就 `ABORT: nav not found`（找不到导航项），
  同一份产物用 `verify_shell.ps1` 却一路全绿：窗口在、插件加载了、截图也正常。
- **[根因]**  symptom 与真因隔了三层。① 跑脚本的会话里 `LANG=en_US.UTF-8`
  （`LC_ALL=C.UTF-8`），**环境变量盖过系统语言**，程序整个起成英文界面——
  机制在第 2 条已记过；② 这些脚本按**中文标签**找控件（`$videoDl = "视频下载"`），
  英文界面下自然一个都找不到；③ 于是报出「导航不存在」，而真因是环境语言，
  与「导航」毫无关系。当时 `ui/language` 是未设置的（= 跟随系统），
  10 个真机脚本里只有 `verify_shell.ps1` 会自己强制写 `ui/language`，
  其余 9 个都假设「默认就是中文」。
- **[正解]** 新增 `scripts/verify/_ui_language.ps1`：`Enter-UiLanguage` 强制写入
  `zh_CN` 并**记住原值**，`Restore-UiLanguage` 复原；两者幂等，且额外注册
  `PowerShell.Exiting` 事件兜住中途 `exit 1` 的 ABORT 路径 —— 否则跑测试的临时
  选择会变成用户下次启动的语言（`verify_shell` 早先只在收尾处复原，中途异常退出
  就会留下 `zh_CN`）。9 个脚本已全部接入，实测 `verify_videodl_fetch` 当场
  下载成功 yt-dlp（17.8 MB）并复原了原值。
- **[守住]** ① 任何按界面文案驱动 UI 的脚本，启动前必须 `Enter-UiLanguage`；
  ② 报错文案要指向真因而不是「找不到控件」——将来看到「找不到 X」，先问
  「X 是不是用另一种语言写的」；③ 周六自动化的报告须把界面语言列为前置条件说明。
- **[同源的两个追加坑（2026-10-06 当晚实测）]** ④ **脚本会把自己的配置删掉**：
  `verify_recent.ps1` 为从干净状态测收藏/最近使用，会 `Remove-Item HKCU:\Software\ToolBox\ToolBox\ui -Recurse`
  ——若守卫写在 wipes 之前，刚写进去的 `zh_CN` **被自己删掉**，应用回落跟随系统、
  界面变英文，脚本却"跑通了"（它要找的中文控件根本不存在）。守卫必须排在 wipes **之后**。
  ⑤ **6 个脚本硬编码 Debug 产物且没有 `-Exe` 参数**：`verify_videodl{,.2,_download,_reuse,_status}`
  与 `verify_recent` 早先把 `bin\Debug\ToolBox.exe` 写死在脚本里，调用方传的 `-Exe` 被静默忽略；
  而 Debug 目录通常只有跑过 deploy 才有 Qt 运行时，于是「换个构建跑」实际换成了另一个产物，
  症状是「功能坏了」而真因是「跑的根本不是那个构建」。现在 6 个脚本统一提供 `-Exe`，
  默认值仍是 Debug 以保持原行为。
- **[第三个同源坑（2026-10-07）]** ⑥ **脚本的缺陷会伪装成产品的缺陷**：补完断言后
  `verify_videodl_download` 报「开始下载按钮 20 秒始终不可用」，第一反应是「产品的
  按钮启用逻辑坏了」。写了个探针去查，结论相反——Release 产物下应用**正确显示**
  `yt-dlp: <路径>`、`enabled=True`，产品无恙；真因是脚本的字段定位靠**下标猜**
  （`$edits[1]` 是地址、`$edits[2]` 是保存目录），而页面新增「共享内核目录」后输入框
  已由 3 个变 6 个，脚本往错误的框里填了地址。另外 QComboBox 在本机**不暴露
  `SelectionPattern`**（`GetCurrentPattern` 抛的是**非终止错误**，被静默吞掉后只打印
  一句 `unreadable`），于是「画质到底改没改成」从来没被验证过。判据换成**按标签文本定位
  同行右侧输入框** + `ValuePattern` 读值。**教训**：断言报红时先问「断言本身对不对」——
  用探针取应用自己的说法，再决定改产品还是改脚本。

## 7. 在 PowerShell 里写检查脚本，然后它「一直绿」

- **[现象]** 给 `verify_coretest.ps1` 加函数级检查（每个导出的 core 函数都要被测试
  引用）时，脚本反复报「全部通过」，可它实际只检查了 2 个函数、后来甚至 0 个。
  更糟的一版报出 17 个「未覆盖」，其中至少 15 个是假的 —— 那是 Qt 私有槽与私有辅助
  方法（`onReadyRead` / `handleLine` / `kindLabel` 之类），它们由元对象系统派发，
  测试**不可能**按名引用。
- **[根因]** PowerShell 5.1 的一连串特性叠加，每一个都让「本该失败的判断」变成通过：
  ① 函数 `return` 多行字符串时，管线会**按行拆成数组**，调用方 `-split` 只看得到第一行；
  ② `-match` **默认大小写不敏感**，`[A-Z_]{3,}` 于是把 `decodeOutput` 这类 camelCase
  名也过滤掉；③ `List[string]` 收到 hashtable 会被转成**字面字符串** `"@{Text=…}"`；
  ④ `ArrayList.Add()` **返回索引**且索引会被当元素，于是冒出「名为 11 的函数」；
  ⑤ `Get-ChildItem -Recurse` 在 Visual Studio 安装目录下**静默返回空**；
  ⑥ 解析类声明时，前向声明 `class QDirIterator;` 会误开一个类体又立刻闭合，
  于是**真正的类体被当成命名空间作用域**扫描；⑦ `python -c` 里的字符串替换若用
  `assert` 才能发现锚点没命中——不写 assert 就是静默跳过。
- **[正解]** **不要在 PowerShell 里解析 C++ 声明。** 改为让编译器说话：读
  `llvm-nm --defined-only --extern-only build/**/Debug/*_core.lib` 的符号表拿到有哪些
  导出函数（MSVC 修饰名里 `?name@namespace@@` 的形状天然可辨，std/Qt 模板实例不带），
  再读 `build/**/Debug/tst_*.cpp.obj` 的**未定义符号**拿到测试实际调用了谁，
  两者取差。零解析、零误报，29 个导出函数全部判定正确。
  （2026-10-08 订正：obj 的路径**不再固定**在 `build/tests/` 下 —— 测试随模块走
  之后，模块自己注册的用例把 obj 放在该模块那一侧，如
  `build/plugins/videodl/...`，故扫描改为 build 全树 + `Debug` 过滤。
  教训的普遍形式不变：**任何钉死某个目录的扫描，都会在目录布局变化那天变成假绿**。）
- **[同日的第二个同类坑]** 同一脚本的 lib 扫描 Filter 写的是 `*_core.lib`，
  而外壳自己的库叫 `ToolBoxCore.lib` —— **名字里没有下划线**，于是 app/core 四个
  模块的函数**从来就不在函数级检查的候选集里**，只有文件级兜着。之所以能发现，
  还是靠反向验证：D3 收官时把 app 侧 6 个测试 obj 全部移走，门禁竟仍然全绿 ——
  「被移走的对象所覆盖的检查不受影响」只有一种解释：**那些对象覆盖的东西压根不在
  检查范围**。修为 `*core*.lib` 后候选从 38 涨到 45，再移一次立刻精确报出 7 个
  MISS。教训的完整表述：**反向验证发现不了「检查范围本身缺了一块」——除非你移走
  的恰好是被漏掉的那块的对象。所以反向验证要移「一整块」，不是移「一个样本」。**
- **[守住]** ① **每个检查脚本写完必须做反向验证**（弄坏一个输入看它是否变红）——
  本例里若只验「全绿」就会把这 7 个坑全带进 CI；② 输入缺失时**报 FAIL 不报 SKIP**，
  「因为没东西可看而通过」也是假绿；③ 一个会误报十几次的门禁比没有门禁更糟——它会被
  所有人忽略，权当没装；④ `-match` 凡涉及大小写敏感的判据，一律用 `-cmatch`。

## 8. 嵌入数字水印「成功」，却永远提取不出来

- **[现象]** 图片数字水印插件（`plugins/imgwatermark`）的载荷层测试全绿（魔数、
  版本、长度、CRC32 四道闸与 CRC 标准向量都过），`embedWatermark` 也返回
  `ok=true`，但 `extractWatermark` 永远报「未检测到有效水印」。**三个不同的错误**
  （alpha 归一化、二维取数索引、逆变换用了正变换）叠加成一个症状。
- **[根因]** 三处都在 DCT 上，且互相掩盖：
  ① **归一化因子写错**：`alpha(u)` 该是 `sqrt(c(u)/N)`（u=0 取 `sqrt(1/N)`、其余
  `sqrt(2/N)`），却写成了 `0.5` / `0.5·M_SQRT1_2`。后果是变换矩阵不再正交，
  **能量不守恒**；
  ② **二维第二趟取数按连续读**：`transformRow(&rows[u])` 取到的是相邻的 `u`
  而不是相邻的 `y`（固定频率下标、遍历空间下标必须按步长 `kBlockSize` 走）；
  ③ **逆变换复用正变换**：正交 A 只满足 `AᵀA = I`，**不等于 `A = Aᵀ`**（基函数
  `cos((2x+1)uπ/16)` 关于 x、u 不对称），复用等于做 `A²`。
  三者都表现为「比特解错、CRC 拦下」，而 CRC 只告诉你「错了」，不告诉你错在哪。
- **[正解]** **把「正逆是否互逆」变成一个可断言的量，而不是靠端到端碰运气**：
  导出 `dctRoundTripResidual()`（对固定的无规律测试块跑一次正变换+逆变换，返回
  逐点最大偏差），配一条断言 `残差 < 1e-9`。写完当场报 `4.4e+02`，把问题从
  「整个算法不work」缩到「正逆不互逆」；修正 ①②③ 后降到 `3e-15`。另用
  **独立实现交叉验证**（另写一份等价的 Python 脚本逐层比对 DC 值与能量和）来确认
  归一化因子，而不是靠反复试参数。
- **[守住]** ① 凡「正变换 + 逆变换」成对出现，必须有一条**直接断言互逆**的测试 ——
  端到端往返失败时，报错只会指向 CRC，不指向变换本身；
  ② 归一化因子先在**一维**上验（DC 应等于 `N·mean`、输入输出能量和相等），再推二维 ——
  一维对了才谈得上二维布局；
  ③ 固定测试块要用**无规律内容**（伪随机噪点）。全零块或纯色块会让任何错误的
  归一化都「看起来正确」，这与测试用纯色图做水印是同一类错误；
  ④ **区分「测试写错」与「代码写错」**：本例中 `stripes` 断言失败（256×256 分 4 带
  装不下载荷而回退到 1 带）是 core 的**正确设计**（冗余与容量此消彼长），
  当时顺手把图换成 512×512 让断言成立，而不是去改 core。改测试前先问「是不是实现的
  预期行为」。

## 9. 系数配对表里 (u,v) 与 (v,u) 并存 → 每 8 比特固定错一位

- **[现象]** 数字水印的 DCT 变换全部修正后（见第 8 条），端到端往返**仍然**失败，
  但错误极有规律：**每8 个比特里固定错第 3 位**（索引 2、10、18…），其余全对。
  像素最大偏移只有 7（肉眼不可见），所以既不像是强度不够，也不像是量化噪声。
  换任何强度（2→20）错误数几乎不变——这本身就是「问题不在强度」的信号。
- **[根因]** 配对表写成 `{1,3},{3,1},{2,4},{4,2},…`，以为「(u,v) 和 (v,u) 是两个不同的对」。实际上配对 (u,v) 用到的下标是 `v*8+u` 与 `u*8+v`，于是 **(u,v) 与
  (v,u) 落到完全相同的两个下标上，只是 A、B 互换**。表里两者并存，就等于让两个
  **不同的比特**去争抢同一对系数：后写的覆盖先写的，嵌入与提取在同一处自相矛盾。
- **[正解]** 表里只保留 `u<v` 的 8 对（`(1,3),(1,5),(2,4),(2,6),(3,5),(3,6),(4,5),(4,6)`），
  并导出 `validateCoefficientPairs()` 断言「各对互不重叠、u<v、不碰直流」，
  配一条 `coefficientPairsAreDisjoint()` 测试守住。
- **[守住]** ① **用独立实现交叉验证**：另写一份等价的 Python 参考实现，同一批
  随机块逐一比对，若参考实现 0错而 C++ 错，错的一定是 C++ 的表/索引而非算法本身 ——
  本例正是靠这一步把「算法不work」缩到「某两位固定错」；
  ② **固定周期的错误是索引问题的signature**：每 N 个单位错同一位，指向「周期内的
  某下标被重复占用」，而不是强度、噪声或阈值；
  ③ 任何「静态配置表」都要有一条断言其**结构性约束**的测试。`(u,v)` 与 `(v,u)`
  这类「看起来不同、实则重合」的关系，评审几乎不可能看出来，但一行断言就能钉住。

## 10. 参数写在系数域：数值「看起来合理」，实际像素改动差 5 倍

- **[现象]** 数字水印嵌入成功后提取失败，逐位比对发现**只剩个别比特错**（如112 位
  错1 位）。加大强度到 20/30/40 后零错误 —— 但此时肉眼能在图上看出明显的块状纹理，
  与工具的承诺（「嵌入肉眼不可见的水印」）直接冲突。
- **[根因]** 强度参数定义在**DCT 系数域**（`target = ±strength`），而用户理解的是
  **像素域**。两者之间隔着 IDCT 的基函数增益：实测「一对系数各改动 d/2」对应的
  **最大像素变化只有 0.16·d – 0.24·d**（随所选中频基函数而异）。于是系数域写
  「强度 40」，落到像素上是 7–10 级 —— 恰好勉强够提取；而要真正做到「不可见」
  （像素变化 ≤3级），系数域只需约 12。**同一份代码，两个数量级的语义错位**，
  而且代码本身看不出任何问题：所有断言都能通过，只是「不可见」这条需求悄悄失守。
- **[正解]** ① 强度一律用**像素域**（0–255灰阶级数）定义，因为那是用户唯一能理解
  也唯一能验收的量；② 在 core 里显式换算 `coefficientStrength = strength / kPixelGainLowerBound`，
  换算系数取实测下界 `0.16`（保守，保证不被放大成可见斑块）；
  ③ 把「最大像素改动」做成**可断言的量**加进测试 —— 这是「不可见」这一定性需求的
  唯一定量守卫。
- **[守住]** ① **凡「用户可调的数值参数」，先问「这个单位的量，用户能预测它会造成什么可见后果吗」**。
  答不上来就说明定义在了错误的域上；② 把定性需求（「不可见」）落成一条数值断言
  （像素改动上限），否则它只是文档里的一句话，没人能验证；
  ③ **「加大参数就变好了」会掩盖单位错位**。本例中把强度调到 40 确实让提取通过了，
  若就此收手，就会交付一个「能跑但会被人一眼看出改过图」的工具。

## 11. 多个系数对在同一块内叠加：像素改动无法由单个系数线性预测

- **[现象]** 「最大像素改动」断言（`embedStaysInvisible`，见第 10 条引入）报 82 级 ——
  远超预期的 8 级，且**调小强度也不降**。逐项测量后发现：把某一对系数差值
  单独推到 10 时像素改动已达 42，推到 100 时是 58 —— **增益高度非线性且快速饱和**。
- **[根因]** 一个 8×8 块里同时调制 **8 对**系数，且这 8 处对应的基函数在**同一个
  像素位置上的取值不同、有的还符号相反**，于是合成效果既可能相互抵消也可能叠加强
  放大，无法用「单对增益 × 数量」推算。前面按单对增益（0.16）做的换算因此从根上
  就不成立 —— 这是**方案层面的建模错误**，不是参数没调好。
- **[正解]** 本条尚未收敛到定论，**如实留档**而非编一个能过的数字。要真正做到
  「像素改动可控」，需要在**像素域**做约束而不是在系数域，例如：
  ① 写入前测量真实像素改动、超预算则回退该块（带「自适应降强度」策略）；
  ② 或直接采用成熟的 DWT-DCT / 量化表嵌入方案，把不可见性写进量化步长的选择里。
- **[守住]** ① **先写「定性需求的数值断言」，再调参数**。本例若先调参数，
  会一路把强度调到能提取为止，然后交付一个「能跑但肉眼可见」的产物；
  ② 凡「N 个独立扰动叠加到一个共享输出」的场景，**不能用单个扰动的增益推断总量**，
  必须实测且承认非线性；
  ③ **遇到反复调参仍不达标时，怀疑模型而不是参数**。本例连换三种强度、
  两种增益口径都无效，才逼出「叠加非线性」这个真正的层次。

## 12. 每块 8 对改1 对：容量的单位从「字节」悄悄变成了「块」

- **[现象]** 为解决第 11 条（块内多对叠加导致像素改动达60+ 级），把`kBitsPerBlock`
  从 8 改成 1（每块只调制一对中频系数）。改完**比特错误率归零、像素改动降到 33 级**，
  但所有端到端用例反而全红 —— 且报错是「未检测到有效水印」，看不出与本次改动有关。
- **[根因]** 两处**按字节书写的容量计算在kBitsPerBlock=1 时全线归零**：
  `stripeCapacityBytes()` 与 `capacityBytes()` 都写成 `blocks * kBitsPerBlock / 8`，
  整数除法下 `blocks * 1 / 8` 恒为 0，于是容量判断永远说「装不下」，可它又走了
  「回退到更少条带」的分支，最终表现为嵌入「成功」但载荷根本没写进去。
  危险之处在于：这些式子在 `kBitsPerBlock = 8` 时**完全正确**，所以此前无人发现。
- **[正解]** ① 两处容量换算都改为**向上取整** `（blocks*kBitsPerBlock + 7）/ 8`，
  并在注释里写明「凡比特→字节换算，必须显式说明向上还是向下」；
  ② 同步修正受影响的测试图尺寸 —— 容量单位从「块数=字节数」变成「块数=比特数」，
  112 比特的载荷原先 128×128 就够，现在需要 256×256；
  ③ 顺带把 `kBitsPerBlock` 改成直接由配对表长度推导，杜绝两处手工同步失配。
- **[守住]** ① **改动一个「贯穿全局的常量」时，先 grep 它出现在哪些换算里**，
  尤其注意带整数除法的：`a*b/8` 这类式子在 b≥8 时永远看不出问题；
  ② **「容量不足」类错误信息要能区分「真的装不下」与「容量算错了」** ——
  本例两者报出的是同一句话，这正是当时难以定位的直接原因；
  ③ 参数表（配对表 / 系数表）与派生的常量（每块比特数）之间，
  优先用 `std::size(kCoefficientPairs)` 这类**编译期求值**建立关系。

## 13. 提取端「读满整条带」vs 嵌入端「写满即停」：长度对不上，CRC 永远判死

- **[现象]** 每块一对 + 像素域闭环之后，像素改动降到 40（不可见断言通过）、
  Python 参考实现**零比特错误**，但 C++ 的端到端往返**依旧全红**，报的还是
  「未检测到有效水印」。而同条件的 Python 参考实现完全正常 —— 说明是 C++ 侧
  的实现差异，且与算法无关。
- **[根因]** 两侧对「一条带里有多少块」的假设不一致：
  嵌入端是「从载荷开头**顺序写满即停**」（`bitCursor >= bits.size()` 就停），
  256×256 有 1024 块而19 字节载荷只需 152 块 —— 后面 872 块**根本没被写过**，
  留着原始图像的系数。而提取端却把**整条带 1024 块全读出来**打包成 128 字节，
  交给 `parsePayload` 后被长度校验拦下（`raw.size() != 9 + 19`），报的是
  「未检测到有效水印」—— 与「我多读了 100 个没写过的块」毫无字面关联。
  早先用 64×64 小图时，带容量恰好≈载荷量，两者相等，问题被掩盖。
- **[正解]** 提取端改为**渐进读取**：先读够一个头部（9 字节），从长度字段
  （第 3–4 字节大端）解析出载荷真实总长，**再补读到那么多为止**。
  配套新增 `expectedPayloadBytes(bits, capacityBytes)`，它顺带用魔数与版本先验一遍，
  不合规就返回 0 表示「这根本不是我们的水印」，调用方回退到读满整条带。
- **[守住]** ① **写入端与读取端的「遍历范围」必须成对设计**，且都要在测试里覆盖
  「图远大于载荷」这个case —— 小图会让两者恰好相等而掩盖问题；
  ② **「长度字段」不只是校验用的元数据，它同时告诉读取端读到哪停**；
  凡「变长记录」嵌入到定长空间，都要有这个机制；
  ③ 报错信息要能区分「没找到水印」与「找到了但长度不对/ 校验不过」——
  本例两者报同一句话，是当时定位耗时的主因。

## 14. 强度换算系数差了 2倍：全部比特整体错，诊断输出全是「随机噪声」

- **[现象]** 第 13 条修好后，「冗余回退」「不修改原图」两条转绿，但端到端往返**仍红**。
  临时加的诊断出口显示：读回的字节是 `a1bcc37f...`（纯随机），而载荷真值是
  `57410100...`（`W` + `A` + 版本 + 长度）—— **首字节就该是0x57**，说明比特从第一位起
  就全错位，而不是「错了几位」。
- **[根因]** 换算系数 `kPixelToCoefficientRatio` 当时取 2.0（实测自「系数幅度 16 ↔
  像素 33」，即每单位系数≈2 级像素），于是默认强度 16 实际只给出**系数幅度 8**。
  而零错误阈值实测在系数幅度 12 —— 8 落在阈值下方，差值裕度不足，符号判断逐块翻转，
  表现为整段比特随机化。用独立Python 参考实现复刻 C++ 的写入逻辑后精确复现：
  `amp=8 → 152 比特错 1 位`、`amp=12 → 0 错`、`amp=16 → 0 错`，与 C++ 表现一致，
  据此把换算系数改为 1.0。
- **[正解]** 换算系数 = 1.0，并把**强度下限抬到实测的零错误阈值 12**：让用户无论怎么拖
  滑块，拿到的都是「能提取」的结果，而不是「成功嵌入却提不出来」。
  另一个关键观察：**最大像素改动几乎不随强度变化**（系数 12→24，像素改动 40→43）——
  改动量由「每块一对」的结构决定，不是强度。所以调强度不影响不可见性，
  应当**放心用足强度**。
- **[守住]** ① **实测标定的常量必须连同「阈值在哪、两边怎么变」一起写进注释**，
  只写「实测得 2.0」会让人以为它是精确值，实际它落在了错误的档位上；
  ② 换算类常量要同时记录**自变量与因变量各扫一遍**的曲线（本文两条数据），
  单点数值无法暴露「差2 倍」这种错误；
  ③ 「读回全噪声」与「读回错几位」是两种不同的病：前者指位序/索引/强度不足，
  后者指个别比特被噪声翻转。诊断输出里**首字节就不对**时，先怀疑位序与强度，
  别急着查 CRC。

## 15. `QImage::pixel()` 触发 detach：写入的是临时副本，交出去的是另一张

- **[现象]** 嵌入端「写完立刻回读第 0 块」得系数差值 **−136.1**（正是调制前的原值），
  而提取端读**同一张图**的同一块得 **+35.96**。两者不可能同时为真，除非它们
  读的不是同一份数据。`maxPixelDelta` 却报41（像素确实变了），`blocks used` 报 144
  （循环确实跑了）。**全部指标都「正常」，只有往返是错的。**
- **[根因]** `readLumaBlock(const QImage&, ...)` 里逐像素调 `image.pixel(sx, sy)`。
  **Qt 的 `QImage::pixel()` 即使在 const 对象上也会触发 detach（写时复制）**，
  把整个像素缓冲区深拷贝一份。于是「读块 → 改系数 → 写块」的循环里，
  每读一次就detach 一次；而 `writeLumaBlock` 拿到的是**非 const 引用**，
  写回的是 detach 之后的那份数据。最终 `result.image = target` 交出去的那张图
  与实际被写入的缓冲**脱节**：像素改动量统计（比较的是 target 与 source）看着正常，
  而提取时通过 `embedded.image` 读到的是从未被写过的原始内容。
  换言之：**改到的是一份临时副本，交出去的是另一份**。
- **[正解]** 改用 `image.constScanLine(sy)` 直读像素：只读、不 detach、且顺带快得多。
  凡「读像素 → 算 → 写回」的图像处理循环，都不要用 `pixel()`。
- **[守住]** ① **`QImage::pixel()` 不是纯读操作** —— 这是 Qt 隐式共享的陷阱，
  与「`const` 成员函数不改对象」的一般直觉相反。凡按像素遍历图像，一律用
  `constScanLine` / `constBits` / `scanLine`；
  ② 出现「同一个值在两处读出不同结果」时，**优先怀疑缓冲区共享与生命周期**，
  而不是继续调算法 —— 两个读点必然有一个读的不是你以为的那份数据；
  ③ **诊断要设在「刚写完」的位置**：正是把回读放在 `result.image = target` 之后，
  才看出了「写入已生效」与「交出去的不是那份」之间的落差。这一步是本次破局的关键。

## 16. 调研成熟实现（OpenStego / JSteg / F5 / QIM）后，确认方案方向并锁定失败边界

- **[背景]** 数字水印已有大量成熟实现（OpenStego 的 DctLSB、JSteg、F5、OutGuess、
  以及 QIM 量化调制）。本条记录对照调研的结论，避免重复踩成熟方案已经踩过的坑。
- **[成熟实现的共同做法]**：
  | 方案 | 载体 | 嵌入位置 | 关键参数 |
  |---|---|---|---|
  | JSteg | JPEG | **量化后**非零 AC 系数的 LSB | 容量中等，chi-square 可检测 |
  | F5 | JPEG | 量化系数 + 矩阵编码 | 改动更少，直方图收缩 |
  | OutGuess | JPEG | 量化系数 + 直方图校正 | 抗二阶统计 |
  | OpenStego DctLSB | **仅无损格式**（显式排除 JPEG） | 中频系数 LSB | 8×8 块、转 YUV、1 bit/块 |
  | QIM | 任意 | 中频系数量化网格 | 步长 Δ，抗压缩最好 |
  共同点：**都在「量化系数域」或「不解码到像素」的前提下工作**；OpenStego 直接把
  JPEG/JPG 从输出格式里剔除。
- **[本项目的处境不同]**：工具是「读入一张 JPEG → 像素域处理 → 输出」，
  必然经历「DCT → IDCT → 量化到 8 级灰阶」的像素往返。实测三方案对照：
  | 方案 | 比特错误 | 最大像素改动 |
  |---|---|---|
  | LSB 替换系数（OpenStego 式） | **74/160** | 0（写回被量化吃掉） |
  | QIM 量化调制（步长 4–64 全试） | **100/160** | 1–22 |
  | **推幅度到 ±strength（当前方案）** | **0/160** | 40–44 |
  结论：**在像素域往返的前提下，系数域的「小幅相对改动」（LSB/QIM）会被灰阶量化
  彻底摧毁，而「推幅度」是唯一能在像素域存活的方案**。这不是臣独创，是被物理
  约束逼出来的唯一解。
- **[吸收进本项目的成熟经验]**：
  ① **容量口径对齐**：OpenStego 也是 1 bit / 8×8 块，与本项目 `kBitsPerBlock=1`
     一致（原先设 8 对/块是错的，已改）；
  ② **中频系数选择**：采纳 zigzag 索引 10–31 为嵌入区的结论（避开 DC 与高频），
     与本项目 `kCoefficientPairs` 的 (u,v) ∈ [1,6] 一致；
  ③ **尺寸向下取整到 8 的倍数**：本项目用夹取（clamp）边缘块，与之等价且更安全；
  ④ **明确告知用户「PNG 才是可靠载体」**：与 OpenStego 排除 JPEG 的做法一致，
     界面已按此提示用户；
  ⑤ **未采纳**：QIM/直方图校正等需要「量化系数域」的技术——本工具的输入输出形态
     决定了拿不到量化表（要拿到需解析 JPEG 码流，属于另一个量级的工程）。
- **[守住]** ① **调研先行**。 mature方案已经把「哪些做法在什么前提下成立」踩过一遍，
  照着做能省掉数天的盲试；本条若早查，第 11 条（块内多对叠加）就不必靠
  「实测扫参」才发现；
  ② 但**调研结论必须与自己的约束对照后再用** —— 成熟方案的前提（量化系数域）
     与本项目不同，照搬会全错。**先问「它的前提我具备吗」**；
  ③ 凡「数值方案」先做三档对照实测（幅度/LSB/QIM），用数据选型，不靠直觉。

## 17. `Format_RGB32` 的内存字节序是 BGRA：按 RGBA 读会互换红蓝通道

- **[现象]** 嵌入侧回读某块系数得 −121.27、提取侧读**同一张图同一块**得 +83.94，
  而独立Python 参考算原图同块为 −136.10。三个数互不相容，且与系数索引、
  缓冲区共享、detach 都无关（那几项已逐一排除）。
- **[根因]** `QImage::Format_RGB32` 在小端机器上的**内存字节序是 B, G, R, A**
  （因为它按 `0xffRRGGBB` 这个 32 位整数存放）。改成scanLine 直读以规避 `pixel()`
  的 detach（第 15 条）时，按直觉写成了 `scan[0], scan[1], scan[2]` 当作 R,G,B ——
  **红蓝被互换**。于是 `qGray(r,g,b) = (11r+16g+5b)/32` 读出来的亮度偏差
  `0.1875·(B−R)` 级（R=10、B=30 时偏 3.75 级），「写入时算的亮度」与
  「读取时算的亮度」对不上，逐块累积后比特全错。
  讽刺的是**换掉 `pixel()` 才暴露** —— 因为 `pixel()` 返回的是已解包的 QRgb，
  通道顺序天然正确；scanLine 更快，于是把这个正确性给丢了。
- **[正解]** 显式按 B,G,R,A 取字节再组装成 QRgb，并在注释里写明「字节序与
  endianness 绑定，换平台同样要改」，不靠 memcpy 之类的技巧掩盖。
- **[守住]** ① **从高级 API 换到底层 API 时，必须逐项核对语义**：
  `pixel()` → `scanLine()` 省了 detach，代价是丢了通道解包。**优化不能悄悄改变语义**；
  ② 性能优化引入的 bug 往往**不在优化点本身**，而在随之改变的其它假设上；
  ③ 「同一个量在两处读出不同结果」这条排查线索又立了一次功 ——
  本条与第 15 条的根因都属于「内存与 API 语义」，而非算法。
  两次都是靠「分别埋点读同一处」才把范围缩到具体读写实现。

## 18. 【终结】像素往返会吃掉系数幅度 —— 必须「写完回读校验」，而不是在系数域自我感觉良好

- **[现象]** 前17 条修完、算法在**纯灰度**参考实现里 152 比特**零错误**之后，
  C++ 的彩色路径仍然全错。写回端的「精确亮度邻域搜索」实测**半径 3 时91.6% 失败、
  半径 32 时仍有 62% 失败** —— 于是绝大多数像素走了兜底平移，亮度不精确。
- **[根因]** 臣一直在**系数域**校验：「把差值推到 ±strength 了」。但真实的链路是
  `DCT 改系数 → IDCT 扩散到 64 像素 → 三通道平移 → 8 级灰阶量化 → 存盘`，
  **像素量化会吃掉一部分差值幅度**。系数域看着达标，落到像素里裕度已不足，
  提取时的符号判断随机翻转 —— 表现为「嵌入成功、提取全错」。
  换句话说：**臣校验的不是真正决定成败的那个量。**
- **[正解]** 改成**像素域闭环**（`embedBlockWithMargin`）：
  写完一块 → **重新从图像读回、重新算该块系数差值** → 裕度不足则**回滚**
  （备份该块像素行）→ **系数幅度加倍**重试，最多 6 轮。
  校验的量从「逆变换前的系数」变成「落盘后的实际差值」——**这才是要保的东西**。
  删掉了那个 91.6% 失败的精确亮度搜索：它是在解决一个**根本不需要解决的问题**
  （亮度精确 ≠系数裕度），复杂却没有收益。
- **[实测】** 闭环版在**完整彩色路径**上：160 比特**零错误**、最大像素改动 **41**
  （与纯灰度参考一致），且没有牺牲不可见性。
- **[守住]** ① **校验的量必须是「最终产物上的量」，不是中间过程的量**。
  本例中系数域达标毫无意义 —— 真正的判据是「存下来的图上还剩多少裕度」；
  ② **「精确地满足某个中间目标」经常是假目标**。亮度精确之所以诱人，是因为它
  看起来很干净、很容易写测试，但它并不决定成败。先问「**这个量决定成败吗**」；
  ③ **穷举搜索在带整数截断的方程上必然失败**。`(11r+16g+5b)/32` 这种整数除法
  让「凑出精确解」变成一个逆映射问题，加半径只是把 91% 失败变成 62% 失败。
  识别这类信号：**当你在调「搜索半径」而不是在改「判据」时，多半走错了路**；
  ④ 凡有「写入 → 读出 → 判断」形态的处理，都应该做成**带回滚的闭环**，
  而不是「算一次、相信它」。

## 19. 「比特数」与「字节数」混用：读取提前 8 倍，长度字段被兜底成 0

- **[现象]** 嵌入与提取读回的字节**逐字节完全一致**（`5741010009266d5c12696e2d6d656d6f72`
  vs载荷 `5741010009266d5c12696e2d6d656d6f7279`），但 `expectedBytes` 报 **17**
  而非18，于是第 18 字节从未被打包，长度校验把**正确数据**拒了，报「未检测到有效水印」。
- **[根因】** `bits.size() >= kPayloadHeaderBytes` —— **左边是比特数，右边是字节数**。
  `kPayloadHeaderBytes = 9`（字节），所以条件在只读到 **9 个比特**时就成立，
  而读满整个头需要 9×8 = **72 个比特**。于是在头部只填了 1 字节多的时候就去解析
  长度字段（第 3–4 字节落在尚未读到的比特上），被组装的兜底 `bitIndex < bits.size()`
  填成 0 -> `bodyLength = 0` -> 函数返回 0 -> 调用方回退到「读满整条带」。
  同一错误在 `expectedPayloadBytes()` 的入口守卫里也有一份。
- **[正解]** 两处都改成 `>= kPayloadHeaderBytes * 8`，并在注释里写明单位。
- **[守住]** ① **凡是「容器计数」与「元素计数」混用的地方，必须在比较处显式写换算**，
  并在注释里点明「左边是X、右边是 Y」。这类 bug 不会崩、不会报错，只是**静静地**
  提前触发某个分支，比空指针难查得多；
  ② **写「至少读到 N 个头」这类守卫时，先问「N 是几个」** —— 是元素个数还是字节数？
  差 8 倍是最容易漏的一档；
  ③ **诊断优先看「数据是否已经正确」而非「是否通过校验」**：本例中读回的字节完全正确，
  只有一处长度对不上。若一开始就打印两边做逐字节 diff，能省掉这一轮。

## 20. 【收官】25 条用例全绿 —— 附本次调试的完整教训清单

- **[结果]** `tst_stego` **25 passed / 0 failed**（含 PNG 无损往返、JPEG q92 有损、
  条带破坏后恢复、纯色图不得解出假水印、容量不足、原图不被修改等）。
  嵌入→提取读回字节与载荷**逐字节一致**，最大像素改动 41（255 的 16%，肉眼不可辨）。
- **[本次共19 条坑，按「是否靠查资料能避免」分类】**：
  | 类别 | 条目 | 能否靠调研避免 |
  |---|---|---|
  | 算法/数学 | 8–12（DCT 归一化、逆变换、配对表冲突、块内叠加非线性、强度换算域） | **能**（调研成熟实现即可看到「系数幅值 vs LSB/QIM」的分野） |
  | API/内存语义 | 15、17（`pixel()` 的 detach、RGB32 字节序 BGRA） | 能（读 Qt 文档可知 `pixel()` 非纯读） |
  | **单位与边界** | 19（比特数 vs 字节数）、12（容量向上取整）、13（读写范围不一致） | **不能**，只能靠「写守卫时问一句 N 是几个」 |
  | **诊断自身** | 连续三次埋点写错（`blockCount` 增量、记错布局、逐轮覆盖） | 不能，且**危害最大**：它会伪造矛盾、误导方向 |
- **[三条最该记住的]**：
  1. **校验的量必须是「最终产物上的量」**。臣在系数域确认「差值推到 ±16」毫无意义——
     像素量化会吃掉它。改成「写完回读、裕度不足就回滚加幅度」后才真正成立（ledger 18）。
  2. **诊断埋点必须与「我要观察的对象」严格对应**。本例连续三次埋点错误：把 `++` 之后
     的计数器当「之前」、记录了错误的块带布局、被后续循环覆盖 —— **每一次都造出一个
     看似无法解释的矛盾**，让人反复去查不存在的 bug。写完自问：「触发时记录的是第几个？
     是哪一次尝试？」
  3. **当你在调「搜索半径」而不是改「判据」时，多半走错了路**。臣把「精确命中亮度」
     的邻域半径从 3 调到 32，失败率只从 91.6% 降到 62% —— 那是逆一个带整数截断的
     方程，加半径永远不成。真正该做的是**放弃这个目标，改校验最终产物**。

## 21. 往 `.ts` 里写译文没转义 XML 实体：`lrelease` 直接 parse 失败

- **[现象]** 补完英文译文后构建失败：`lrelease error: Parse error at toolbox_en.ts:408:37:
  Expected '#' or '[a-zA-Z]', but got ' '`。构建阶段失败，而非编译阶段。
- **[根因]** 译文里写了 `Output format & quality`，那个 `&` 是**裸的 XML 实体起始符**。
  `.ts` 是 XML，`&` 必须写成 `&amp;`。中文原文里没有这个问题（`&` 极少出现），
  所以平时不会遇到；一旦译文出现 `&`（`A & B`、`Q&A`）就必然踩到。
- **[正解]** 写入后统一扫一遍译文节点里的裸 `&`（正则 `&(?!amp;|lt;|gt;|quot;|apos;|#)`）。
- **[守住]** ① **程序化写 `.ts` / `.tsv` 等 XML 文件时，正文必须经过 XML 转义**
  （`&`、`<`、`>`、`"`），哪怕脚本跑一次就删 —— 转义错了报错位置在 `lrelease`，
  与写它的脚本八竿子打不着，定位成本很高；
  ② 同类需转义的还有 `<`、`>`（本项目译文里出现过 `PNG（无损，水印最可靠）` 这类
  含全角括号的还好，若是半角 `<` 就同样会炸）。
